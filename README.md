# Flight Scheduler

Vue 3, Vite, JavaScript, SCSS로 만든 항공사 운영 퍼즐 게임입니다. Nuxt를 사용하지 않습니다. 가상 기체 AS01~AS06에 고정된 왕복 운항 블록을 배정합니다.

## 실행

Node.js 20.19 이상 또는 22.12 이상에서 실행합니다. 개발과 검증은 Node.js 24에서 수행했습니다.

```sh
npm install
npm run dev
npm test
npm run build
npm run preview
```

개발 서버 주소는 터미널에 표시됩니다. 기본 주소는 http://127.0.0.1:5173 입니다. 외부 API 키와 서버 없이 실행하며, 시간표 스냅샷을 저장소에 포함합니다.

## GitHub Pages 배포

```sh
npm run deploy
```

`predeploy`가 `/flight-scheduler/` 경로를 기준으로 프로덕션 빌드를 수행한 뒤, `gh-pages`가 `dist`의 파일을 `yheun03/flight-scheduler` 저장소의 `gh-pages` 브랜치에 커밋하고 push합니다. 기본 `npm run build`와 로컬 개발 설정은 유지합니다. GitHub에 push할 수 있는 Git 인증과 저장소 쓰기 권한이 필요합니다. 토큰을 소스에 넣지 말고 기존 Git credential manager를 사용하세요.

첫 배포 후 [저장소 Pages 설정](https://github.com/yheun03/flight-scheduler/settings/pages)에서 다음을 한 번 설정합니다.

1. Build and deployment의 Source를 `Deploy from a branch`로 선택합니다.
2. Branch는 `gh-pages`, 폴더는 `/ (root)`로 선택하고 저장합니다.
3. Pages 배포 작업이 끝나면 [Flight Scheduler](https://yheun03.github.io/flight-scheduler/)에서 확인합니다.

이후에는 `npm run deploy`로 갱신할 수 있습니다. 배포용 `gh-pages` 브랜치에는 빌드 결과만 들어가며, 소스 브랜치의 커밋과 push는 별도로 관리합니다. `.nojekyll` 파일을 생성해 Jekyll 처리를 생략합니다. 배포 명령은 해당 브랜치의 기존 배포 파일을 현재 빌드 결과로 갱신합니다.

참고: [Vite 정적 배포](https://vite.dev/guide/static-deploy), [gh-pages 사용법](https://github.com/tschaub/gh-pages#command-line-utility).

## 구현한 기능

- 에어서울 최하 난이도, 가상 기체 6대. AS01~AS04는 ICN, AS05~AS06은 GMP에서 시작합니다.
- 기준 주간 2026-11-16~11-22, 주간 보기 전용 가로 스크롤, KST 공통 시간축.
- HTML 버튼으로 구현한 왕복 블록과 비행, 현지 대기, 복편, 귀환 후 준비 구간 표시.
- 기체 배정 후 해당 블록 위치로 자동 스크롤하며, 상세에서 배정 위치를 다시 확인할 수 있습니다.
- 기체 행 드래그 배정, 행 사이 이동, 보관함 드롭 해제. 수평 이동으로 예정 시각을 바꾸지 않습니다.
- 터치와 키보드에서 블록 선택 후 상세의 기체 메뉴로 동일하게 배정합니다.
- 각 기체의 초기 비행 시간과 사이클, 고정된 필수 정비.
- 변경 1회를 1단위로 하는 되돌리기와 다시 실행. 전체 해제도 1단위입니다.
- localStorage 수동 저장과 불러오기, sessionStorage의 현재 탭 새로고침 복원.
- 형식 버전, 데이터셋 ID, 플레이 ID를 검증합니다. 다른 데이터셋이나 버전, 손상, 중복 배정은 적용하지 않고 안내합니다.
- 저장 초기화는 수동 저장 데이터만 제거하고 현재 배정을 유지합니다.
- UTC 기준 운영 검증, 오류 목록에서 블록 선택, 비용과 가중치가 포함된 결과 리포트.
- 클리어 플레이 ID 중복 방지. 결과 재열기, 새로고침, 같은 저장 불러오기로 횟수가 늘지 않습니다.
- 다른 항공사와 난이도는 준비 중으로 표시합니다. 진에어 마스터 3회에 한한 실무 해금 판정 로직을 분리해 검증했습니다. 현재 다른 항공사 플레이는 없습니다.
- 모바일에서 타임라인 크기를 줄이지 않고 가로 스크롤을 제공합니다. 날짜 헤더와 기체 열은 타임라인 스크롤 영역 안에서 고정됩니다.

처음에는 3개 왕복이 예시 배정되어 있고 AS01에 충돌이 있습니다. 후쿠오카 왕복을 AS02로 옮기며 시작할 수 있습니다. 새 플레이 시작은 새로운 플레이 ID와 예시 배정을 만듭니다.

## 데이터와 시간 계산

- 원본 항공편: `flights`. 편명, 공항, 현지 날짜와 시각, 출발과 도착 IANA 시간대, 오프셋을 포함한 ISO 예정 시각, 출처 ID를 가집니다.
- 게임 왕복: `rotations`. 명시적인 왕편 ID, 복편 ID, 귀환 준비 시간과 필수 여부입니다.
- 배정: `assignments`. 왕복 ID와 기체 ID만 연결합니다. 원본 편의 시간은 변경하지 않습니다.
- 시나리오: `aircraft`, `rules`, `maintenance`, `boundaries`를 분리합니다.

시간 비교는 ISO 예정 시각을 UTC epoch로 변환해 수행합니다. HH:mm 문자열을 비교하지 않습니다. 포함한 날짜와 공항의 시간대 오프셋을 명시적으로 기록했으며, 임의의 공항이나 DST 날짜를 입력받는 범용 시간대 변환기는 구현하지 않았습니다. 새 데이터셋을 추가할 때는 IANA 시간대와 해당 날짜의 오프셋을 함께 검증해야 합니다.

기체의 비행 시간은 두 편의 예정 출도착 차이 합계이며, 현지 대기와 귀환 후 준비는 포함하지 않습니다. 초기 운항 시간과 사이클은 이번 시나리오 한도에서 이미 사용한 가상 부담입니다. 비행 1구간은 1사이클로, 모든 현재 왕복은 2사이클입니다.

화면 밖으로 나간 블록은 CSS 영역에서만 잘라 표시합니다. 실제 시작과 종료 epoch, 비행 시간과 검증 범위는 유지합니다.

## 게임 규칙과 경계

준비 시간과 정비, 비용 수치는 실제 항공사 규정이나 수리비가 아닙니다.

- 목적지 최소 준비 30분, 귀환 후 준비 45분, 추가 지연 대응 목표 30분.
- 기체별 초기 부담을 포함한 62시간과 30사이클 한도.
- 기체별 수요일 2시간 필수 정비. 고정 위치에서 수행하며 생략과 삭제를 허용하지 않습니다.
- 기체의 첫 출발 공항은 고정하지 않지만, 연속 운항 사이에는 기체를 자동 이동시키지 않습니다.
- 시간 중복, 귀환 준비 부족, 목적지 준비 부족, 공항 연결, 중복과 미배정, 정비 중복, 부담 한도, 주간 시작과 종료를 검사합니다.
- 일회성 모드의 인접 조건은 직전 주 월요일 기준 시작 1시간 전 도착, 월요일 00:00 준비 완료, 다음 주 월요일 12:00 출발하는 가상 시간 경계입니다. 실제 인접 주 운항 자료로 주장하지 않습니다.
- 가상 연습에서 주간 반복 검사를 켜면 직전 주와 다음 주의 운항 및 정비 블록을 함께 비교합니다. 왕복이 경계를 넘더라도 원본을 잘라 검사하지 않습니다.

## 점수와 클리어

100점 만점의 실시간 누적 점수는 과제 완료 40점, 여유 25점, 분산 20점, 비용 효율 15점으로 구성됩니다. 필수편을 모두 배정한 초기 만점 상태에서 시작하는 방식은 아니며, 계획에 따라 0~100점으로 평가합니다.

- 완료: 필수 왕복 배정 비율 × 40.
- 여유: 각 목적지의 최소 준비 이후 추가 여유와 같은 기체의 다음 편까지 귀환 준비 이후 여유를 각각 30분으로 나눠 0~1로 제한한 평균 × 25. 미배정 이외 오류 수 + 1로 나눕니다.
- 분산: 초기 부담을 포함한 6대의 비행 시간과 사이클 상대 평균절대편차를 각각 구합니다. `20 × max(0, 1 − (시간 편차 + 사이클 편차) / 4)`.
- 비용 효율: `15 × (1 − 사용 기체 수 / 6 × 0.15)`.
- 각 항목을 소수 첫째 자리까지 반올림하고, 합계를 정수로 표시합니다.

필수편을 빼서 점수를 높일 수 없도록, 완료 이외 3개 항목은 필수편 전체 배정 후에만 지급합니다. 모든 필수편을 배정한 계획은 최소 40점이며, 미완성 계획은 40점 미만입니다. 필수 정비는 항상 포함됩니다. 클리어 조건은 필수편 전체 배정, 전체 검증 오류 0건, 80점 이상입니다.

연료는 전체 필수편 비행 시간 × 420, 정비 적립은 전체 필수편 시간 × 110 + 사이클 × 70, 필수 정비는 블록 수 × 180크레딧입니다. 이 값들은 기체 재배정과 미배정으로 바뀌지 않습니다. 배정에 따라 변하는 비용은 사용 기체당 120크레딧입니다. 정비 적립과 필수 정비 수행 비용을 구분합니다.

## 코드 구조와 참고

- `src/App.vue`: 화면과 한 화면에서 쓰는 상태, 배정과 이력, 저장 UI.
- `src/components/FlightBlock.vue`: 타임라인과 보관함에서 재사용하는 접근 가능한 왕복 버튼.
- `src/components/AppIcon.vue`: 화면 공통 SVG 아이콘.
- `src/data/schedules.js`: 원본 스냅샷, 출처, 명시적 왕복 연결, 가상 시나리오와 게임 설정.
- `src/game.js`: 화면과 독립적으로 검증 가능한 UTC 운영 검증, 점수와 저장 형식.
- `src/assets/styles.scss`: 의미 기반 SCSS 변수, 공통 스타일과 BEM.
- `tests/game.test.js`: 운영 규칙과 저장 회귀 테스트.

빈 저장소에 기존 컴포넌트는 없었습니다. [framework](https://github.com/yheun03/framework)의 실제 `src/components/AppButton/AppButton.vue`, `src/assets/styles/abstract/_variables.scss`, `src/assets/styles/components/base/_button.scss`를 확인했습니다. `<script setup>`, BEM modifier, 의미 기반 변수와 공통 버튼 스타일을 참고했습니다. 저장소 설명 페이지의 구조와 현재 API tree가 달라 실제 파일 경로를 재확인했습니다. Nuxt 설정, RouterLink 의존성, 범용 props와 유틸 체인은 복사하지 않았습니다.

드래그는 브라우저 기본 HTML Drag and Drop, 터치와 키보드는 네이티브 select를 사용합니다. 날짜는 명시적 ISO 오프셋과 Intl.DateTimeFormat으로 처리할 수 있어 날짜 및 드래그 라이브러리를 추가하지 않았습니다. 참고 이미지 첨부는 현재 대화에서 확인되지 않아 요청한 정보 구조를 기준으로 디자인했습니다.

## 검증한 내용

- `npm run build`: Vite 프로덕션 빌드 통과.
- `npm test`: Node 내장 테스트 러너로 18개 통과.
- 테스트 범위: 부분 자료 날짜와 출처, 정상 클리어, 공항 불일치, 시간 중복, 중복과 미배정, 귀환 후 준비, 목적지 준비, 잘못된 왕복 연결, 정비 중복, 시간과 사이클 한도, UTC+7 자정 넘김, 직전/다음 주 경계, 반복 경계, 고정 비용 불변, 필수편 누락 점수 제한, 저장 손상/버전/데이터셋/중복 검증, 클리어 중복 방지, 원본 불변.
- 브라우저 실조작: 기체 select 배정, 공항 불일치 오류 표시, 되돌리기와 다시 실행, 기체 행 드래그, 보관함 드롭, 수동 저장 후 전체 해제와 복원, 새로고침 복원, 8개 왕복 전체 배정과 91점 클리어.
- 브라우저 콘솔에서 오류와 경고가 없음을 확인했습니다.
- 390px 모바일 폭과 1440px 데스크톱 폭을 확인했습니다. 타임라인의 가로 스크롤과 기체 열 고정을 제공합니다.

## 예정 기능과 미확인 범위

- 공식 자료의 기준 주간 전체 수집, 날짜별 운항 여부와 편명 변경 매핑의 검증.
- 실제편 스냅샷의 자동 수집이나 실시간 갱신은 제공하지 않습니다.
- 나머지 항공사 시나리오와 실무 난이도 콘텐츠.
- 임의 공항/DST 날짜를 위한 범용 시간대 데이터 입력.
- 기체 수와 정비 규칙 편집, 서버 저장, 계정 동기화는 현재 범위에 포함하지 않습니다.
- 드래그의 자동 스크롤은 브라우저 기본 동작을 따릅니다. 모바일에서는 상세의 배정 메뉴를 권장합니다.
